PRINCIPLES (hold across sprints)
================================================================

- Batch-in-memory reads, never N+1 (NFR-6): `GET /members` (S1),
  `GET /api/karya` roster (S2), feed/featured (S3). Fine at community
  scale; revisit only if a listing grows large.
- Server-side authorization, never trust the client: owner-only
  approve/decline (S2.10, incl. the `pendingRequests` field S2.8),
  member-only posting (S3.7), admin-only featuring (S3.10a). The Playwright
  e2e mocks the API, so it covers the UI gate (e.g. no compose box for
  non-members), NOT this boundary — the karya-authz suite exercises the real
  router for the 401/403/404 paths.
- Closed vocabularies as validated `text`, not pg enums, so the list stays a
  code change not a migration: stages (S2), post `kind` / `role` / `status`
  (S3). Matches repo `skills` style.
- Shared cores kept entity-agnostic for reuse: interest catalog +
  `slugifyInterest` (S1 → S2 `karya_interests` / `reconcileKaryaInterests`;
  keep find-or-create reusable for FR-16 problems next); `toKaryaListItem` /
  roster + interest batching (S2 → S3 feed).
- No RBAC / admin app / moderation build-out — the PRD describes none: env
  `ADMIN_EMAILS` allowlist, not `users.role` (S3); no tag merge UI (S1). The
  toggle is UI convenience; the server email check is the real authority.


================================================================
SPRINT DECISIONS (the specifics behind the principles)
================================================================

S1 — Interests + profile
- Tag fragmentation (PRD §15, DECISION-D): slug dedupe is the primary guard,
  curated-first suggestions in the editor (S1.9) the secondary nudge.
  User-created rows accumulate `curated:false` for later promote/merge.
- `handle` stays unique-but-nullable (carried from S0a.6); a NOT NULL
  tightening is out of scope.

S2 — Karya core
- No real profile pics (DECISION-E): faces are monograms; the wire carries a
  nullable `image` so an upload feature is drop-in later. Don't build it here.
- Single-owner model (one `role:"owner"` row) is the only authority;
  co-owners/transfers out of scope.
- Stages stored as a `jsonb` string array validated by `normalizeStages`
  (see Principles — adding/reordering stays a code change).
- Posts deferred to S3 (DECISION-F): placeholder empty-state only, no
  `posts` table, no compose. Resisted scope-creeping posts in.

S3 — Posts, feed & homepage
- Admin = env allowlist (DECISION-A): `ADMIN_EMAILS` parsed in `worker.ts`,
  checked server-side on `…/feature`. Editing it needs a redeploy/secret
  update — acceptable for a small founding team. The seeder pre-marks
  featured karya so a fresh seed isn't empty.
- Homepage regression is intentional (DECISION-F): the AI-discovery chat +
  members list were pulled from `/home`, shifted to S4 (discovery + search).
  Member-browsing survives the gap only via faces/titles linking out —
  confirm those links exist. S4 rebuilds the discovery `callClaude` code;
  don't leave it as dead weight.
- Feed shape (DECISION-E): merge in memory, batch enrichment (see
  Principles). No ranking, no cursor — a fixed `limit` is the whole
  pagination story. The `oneOf`/discriminated `FeedItem` stays simple for
  orval/zod codegen: a flat `type` discriminant, not deep polymorphism.
- Post `kind` (DECISION-B): validated `text`; `normalizePostKind` returns
  `null` (no default) because a post must declare its kind → API maps
  `null` to 400.
- Likes/comments are out (FR-20 P1 / FR-21 P2) — posts are author-only
  content. The feedback/validation channel (FR-42) and per-project AI
  (FR-33) are P1; don't scope-creep them onto the post stream.

HARDENED (work done post-Sprint 3)
================================================================

- API authz suite (apps/api/tests/karya-authz.test.ts, 16 tests). Mounts the
  REAL karya router with an injected chainable db + configurable auth, driven
  via `app.request` — asserts the real 401/403/404/400/200 flow and that a
  post is inserted with the session user as author (not client-supplied).
  `pnpm test:api` now runs a real suite (was: no test files, exit 1).
  Reusable seam: tests/helpers/harness.ts `createDbMock`.
- Stale template specs (auth.spec / routes.spec) carried RED for 3+ sprints
  (asserted a "My App" shell / `/api/items` / a 404 page this app never had)
  rewritten to the real app (welcome / login / feed-first home). Lesson:
  knowingly-red tests desensitize you to red — fix-on-touch or delete.
- Migration drift guards — three CI checks (.github/workflows/ci.yml), one
  per axis along which schema, files and DB can diverge:
    1. `pnpm db:check` (no DB) — every migration .sql is registered in
       meta/_journal.json. The runner applies files by the journal, not the
       directory, so a stray file is silently ignored.
    2. `pnpm db:generate` + dirty-tree check (no DB) — the schema TS isn't
       ahead of the migrations. generate diffs schema against the snapshots
       (it never connects to a DB); a new emitted migration dirties the tree.
    3. `pnpm db:migrate` on a clean Postgres service container — the
       generated SQL actually applies (ordering / FKs); db:push never
       exercises this locally.
  Removed orphan `0001_add_profiles_and_matches.sql` (superseded duplicate of
  the journaled `0001_panoramic_cable`, which also drops the template `items`
  table). Lesson: db:push keeps the *db* correct while letting the migration
  *files* drift unnoticed; tsc already guards schema-typo bugs, so the
  residual gap is runtime queries vs. the real DB (see Open / Deferred).

- Tier 1 preview deploys (.github/workflows/preview.yml). On every PR,
  `wrangler versions upload` built a Worker version (no production traffic
  shift) and a sticky bot comment posted its *.workers.dev URL — turning
  commit-straight-to-main into branch-and-eyeball. Gated on
  CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID, no-op until set (same
  secret-guard idiom as release.yml).
  SUPERSEDED — deleted in 15cdbb2. It ran against *prod* bindings incl.
  DATABASE_URL, and better-auth derives baseURL from APP_URL, so login was
  broken on the *.workers.dev origin: the preview could not exercise anything
  behind auth, while still exposing prod data. Mockup PRs kept an isolated
  static preview (preview-mockups*.yml). App previews: see
  plans/how-to/preview-environments.md.


================================================================
OPEN / DEFERRED (flagged, not P0)
================================================================

In-sprint forward-looks already flagged: `handle` NOT NULL (S1); photo
upload, co-owners/transfers (S2); likes/comments, feedback channel,
per-project AI (S3).

- Real-Postgres query coverage. The authz suite mocks the db, so it proves
  guard ordering + control flow, NOT that the Drizzle queries are valid SQL.
  A testcontainers / docker-compose-DB integration harness would add query
  validity + FK/cascade coverage. The CI from-scratch apply proves migrations
  run, not that runtime queries match the schema. Deferred per NFR-6 —
  revisit if a query bug reaches production.

- Admin / moderation UI. The env-config-plus-SQL stance has held through P0,
  but the seams show: the featured set has no see/reorder surface (rank edits
  mean raw SQL on `featured`); granting/revoking an admin is a redeploy, not
  an action (`ADMIN_EMAILS`) — the point a real `users.role` / `admins` table
  earns its keep; tag/interest merge/promote/dedupe has no home, so
  `curated:false` rows accumulate unmanaged; no hide/remove/flag surface for
  posts/karya exists. Pick up once curation, allowlist churn, or tag cleanup
  becomes a recurring manual chore.

- Preview deployments — per-PR ephemeral environments. Tier 1 was deleted, not
  promoted (see HARDENED). The Neon-branch-per-PR sketch that used to live here
  is dead twice over: the stack is moving off Postgres to D1 (#40), which has
  no branching; and copy-on-write from prod was itself the hazard, since every
  preview URL would then be a public window onto real student PII. Preview DBs
  are 100% seed data — create, migrate, seed, delete. Ratified decisions in
  plans/how-to/preview-environments.md; discussion in #23.
  Unblocked once #40 landed. Provisioning (create/migrate/seed/deploy) shipped
  in #44 as .github/workflows/preview.yml; teardown + scheduled reaper + a live
  concurrency cap shipped in #45 (preview-teardown.yml, preview-reaper.yml, and
  the shared .github/scripts/preview-reaper.mjs).
