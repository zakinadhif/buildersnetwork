# Sprint 3 — Posts, feed & homepage

*Part of the [Roadmap](../roadmap.md). PRD: [al-fath-berkarya-prd.md](../al-fath-berkarya-prd.md) · Vision: [al-fath-berkarya-vision.md](../al-fath-berkarya-vision.md). Non-authoritative working knowledge — trust the code when they diverge.*

Goal: the flywheel — karya feel alive (members post updates), and there's a place to see activity (a reverse-chron feed + a curated homepage).

- [x] **FR-18** Karya members post updates: `progress / challenge / achievement`.
- [x] **FR-19** Posts appear on the karya page **and** in the feed.
- [x] **FR-22** Reverse-chronological feed of recent posts + new karya. **No ranking** (Risk §15: avoid the attention-trap).
- [x] **FR-23** Homepage: hand-curated "Top picked inspiring projects" + recent feed.
- [x] **FR-24** Team marks a karya "featured" — `featured` table, edited in-app via an `ADMIN_EMAILS` allowlist toggle (no RBAC).

New tables: `posts`, `featured`.

**Exit:** posting an update surfaces it on the karya page and the global feed; the homepage shows featured picks + the recent feed. (Success metric: *% who post a second update* becomes measurable here.)

> **Decisions resolved** (2026-06-21):
> - **(A) Curation is an in-app toggle gated by an `ADMIN_EMAILS` env allowlist — no RBAC.** The PRD describes *no* administration surface — "admin" appears only as the *actor* in FR-24 ("(P0, admin) Team can mark a karya featured"), and the `User` data model (PRD §10) carries **no `role`/`is_admin` field**. "Team" is the small founding team (Phase 0). So rather than build a role system (against **NFR-6**), the team is a short **`ADMIN_EMAILS`** allowlist (comma-separated, parsed in `worker.ts` like `ALLOWED_ORIGINS`, surfaced on the request context). It gates `POST`/`DELETE /api/karya/:id/feature` (server-side, 403 otherwise) and a ✦ **feature toggle** rendered on the karya page only for allowlisted viewers. This reuses the existing env-free `@student.telkomuniversity.ac.id` sign-up gate pattern (`app.ts`) — no schema beyond the `featured` table, no `users.role`, no separate admin app. The seeder (S3.5) still pre-marks a couple karya so the homepage isn't empty on a fresh seed, but **ongoing curation is the toggle, not SQL**. *Email membership in an env list is the entire authority model this sprint; a real admin role / audit trail is out of scope.*
> - **(B) Post `kind` is a fixed-enum `text` column guarded by a pure validator — mirrors stages (Sprint-2 DECISION-B).** `kind ∈ {progress, challenge, achievement}` is a *closed* vocabulary (not a growing, browsable one like interests), so store it as plain `text` (repo style: `role`/`status`/`skills`/`stages` — not a pg enum) and guard writes with a pure `normalizePostKind(input): PostKind | null` in `libs/db/src/posts.ts`. `PostKind` is a TS string-literal union + `POST_KINDS` const tuple. Pure + import-light → unit-testable without a DB, shared by the API save path and the seeder (mirrors `karya.ts`/`interests.ts`).
> - **(C) Anyone with an approved membership may post (FR-18: "any karya member").** Authorization = the session user has a `karya_members` row with `status:"member"` for that karya. The owner qualifies via the owner+member row (Sprint-2 DECISION-G). `status:"pending"` requesters and non-members get **403** — verified server-side, never trusted from the client (same posture as Sprint-2 approve/decline).
> - **(D) One `posts` table, two read paths — no duplication (FR-19).** Posts are keyed by `karya_id`. "Appear on the karya page **and** the feed" = two reads over the same rows: (1) the **karya stream** (`GET /api/karya/:id/posts`), (2) the **global feed** (`GET /api/feed`, merged with new karya). The compose box lives on the karya page (members only). The stream is a **separate endpoint/hook**, not folded into `GET /api/karya/:id` — so posting can `refetch` the stream without re-fetching the whole detail (roster/pending).
> - **(E) The feed is a merged, reverse-chron, in-memory union of two item types — no ranking (FR-22, Risk §15).** `GET /api/feed` fetches the N most-recent **posts** and the N most-recent **karya**, tags each with a discriminated `type` (`"post" | "karya"`), merges by `createdAt` **descending**, and slices to a fixed `limit` (50). **No scoring, no infinite-scroll, no cursor pagination** this sprint (community scale, NFR-6). Enrichment is batched, never N+1 (reuse the Sprint-2 `rostersByKaryaIds` / `interestsByKaryaIds` + a shared `toKaryaListItem` builder): a post item carries its author face + `kind` + `body` + a `{id,title}` reference to its parent karya; a karya item carries the full `KaryaListItem` shape.
> - **(F) Homepage is restructured feed-first (user decision).** `CommunityHome` becomes **"Top picked inspiring projects" (featured) + recent feed** as the primary content. The **AI-discovery chat and the members list are removed from `/home`** — they are a Sprint-4 *search/discovery* concern ([Sprint 4](sprint-4.md): "Project discovery page … replaces the bare members-list as the projects home"). Keep the "+ buat karya" entry. To avoid stranding people-browsing for one sprint, **faces and titles in the feed/featured link out** (post authors → `/member/:id`, karya → `/karya/:id`). Sprint 4 reclaims the full discovery + search surfaces. *(Deliberate regression vs. the Sprint-2 home; the discovery `callClaude` logic is removed, not parked as dead code — Sprint 4 rebuilds it on the search page.)*

## Data model

```
posts
  id          text pk            -- crypto.randomUUID()
  karya_id    text -> karya.id  on delete cascade  not null
  author_id   text -> users.id  on delete cascade  not null
  kind        text not null      -- "progress" | "challenge" | "achievement"  (PostKind, DECISION-B)
  body        text not null
  created_at  timestamp not null default now()
  index on (karya_id)            -- karya stream (DECISION-D)
  index on (created_at)          -- reverse-chron global feed (FR-22)

featured
  karya_id    text pk -> karya.id  on delete cascade
  rank        integer not null default 0   -- hand-curated order; lower sorts first ("Top picked")
  created_at  timestamp not null default now()
  index on (rank)                -- ordered "Top picked" read
```

`kind` is plain `text` (not a pg enum), validated by `normalizePostKind`, matching the repo's string-literal style (`role`/`status`/`stages`) and keeping the vocabulary a code change, not a migration. `featured` is one row per featured karya; `rank` gives the team explicit ordering for the homepage "Top picked" section. `PostKind` is a TS string-literal union validated by a pure helper, not a DB-level enum. No `author_id` index this sprint — a member's-own-posts view is microblog territory (FR-35, P1); add it then.

## Exit

A karya member opens a karya page, writes a `progress` / `challenge` / `achievement` update in the compose box, and posts it — it appears immediately in that karya's reverse-chron stream and in the global feed; a non-member sees the stream but no compose box, and is rejected server-side (403) if they try to post. An allowlisted team member (email in `ADMIN_EMAILS`) sees a ✦ feature toggle on a karya page and can mark/unmark it featured; non-admins never see it and are rejected (403) server-side if they try. `/home` is feed-first: a hand-curated "Top picked inspiring projects" section (from the `featured` table) sits atop a reverse-chron feed interleaving recent posts and newly created karya — no ranking, no infinite scroll. Faces and titles link out to member and karya pages. Unit tests cover post-kind normalization; an e2e covers post → stream + feed render and the featured/feed homepage. Migration generated, seeders idempotent and `--reset`-safe, README touched.

## Risks / notes

- **Admin is an env allowlist, not RBAC (DECISION-A).** Curation is a karya-page toggle gated by `ADMIN_EMAILS` (parsed in `worker.ts`, checked server-side on `…/feature`). There is **no `users.role`, no admin role, no separate admin app** — the PRD describes none. Resist growing this into RBAC. The toggle is UI convenience; the server email check is the real authority. Editing the allowlist requires a redeploy/secret update — acceptable for a small founding team. The seeder pre-marks featured karya only so a fresh seed isn't empty.
- **Homepage regression is intentional (DECISION-F).** Removing the AI-discovery chat + members list from `/home` is a deliberate scope shift to Sprint 4 (discovery + search), not an accident. Member-browsing survives the gap only via faces/titles linking out — confirm those links exist before closing. Don't leave the discovery `callClaude` code as dead weight; Sprint 4 rebuilds it.
- **Feed cost + shape (DECISION-E).** Merge in memory, batch enrichment (reuse `rostersByKaryaIds`/`interestsByKaryaIds`/`toKaryaListItem`) — fine at community scale (NFR-6). No ranking, no cursor: a fixed `limit` is the whole pagination story this sprint. Revisit only if the feed grows large. The `oneOf`/discriminated `FeedItem` must stay simple enough for orval/zod codegen — a flat `type` discriminant, not deep polymorphism.
- **Authorization is server-side (DECISION-C).** "Any karya member can post" means `status:"member"` verified on the server for `POST …/posts` — never trust a client flag. Pending requesters and non-members get 403.
- **Post `kind` as enum vs. pg enum (DECISION-B).** Stored as validated `text`, not a DB-level enum — matches `stages`/`role`/`status` and keeps the vocabulary a code change. `normalizePostKind` returns `null` (no default) because a post must declare its kind; the API maps `null` → 400.
- **Likes/comments are out (FR-20 P1 / FR-21 P2).** Posts this sprint are author-only content — no reactions, no threads. The feedback/validation channel (FR-42) and per-project AI (FR-33) are P1; don't scope-creep them onto the post stream.
